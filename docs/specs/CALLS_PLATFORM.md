# Luxora Calls Platform Contract

**Canonical public release:** Beta-0.1  
**Owner and developer:** Flenym  
**Status:** target contract plus a local infrastructure scaffold; calls are not implemented

## 1. Decision

Luxora will own call authorization, lifecycle, membership, privacy and product
semantics while using a maintained WebRTC media plane. The initial reference
stack is LiveKit Server for SFU transport and coturn for relay. Luxora will not
build codecs, ICE, DTLS, SRTP, congestion control or an SFU from scratch.

This decision does not make calls available. The current repository has no call
control records, grants endpoint, webhook reconciliation, push/ringing flow or
client media session. `docker-compose.calls.yml` is only a configuration probe.

## 2. Trust boundary

Default WebRTC transport encryption protects media on each network hop. It is
not Luxora Private end-to-end media encryption: the SFU is inside the media
trust boundary and no audited per-device media-key protocol exists yet. Neither
the UI nor documentation may show “protected call”, E2EE or equivalent copy
until the independent media-E2EE gates pass.

The call control service may know call ID, conversation ID, invited/joined
devices, state transitions, track classes, coarse quality and timing. It must
not log SDP, ICE credentials, IP addresses beyond short security retention,
media payload, screen content, captions or stable participant labels in metrics.

## 3. Authoritative identifiers

- `callId`: opaque UUID generated by the server.
- `clientNonce`: caller-scoped idempotency key for creation.
- `roomName`: random internal media-room identifier, never a conversation ID.
- `epoch`: monotonically increasing membership/security generation.
- `revision`: optimistic concurrency value for control-state mutations.
- `participantIdentity`: opaque call-scoped device identity, not username.
- `trackId`: media-plane identifier mapped server-side to a source class.

Media metadata must not contain display names, message text, phone numbers or
other durable account identifiers. Clients receive the presentation roster
from authorized Luxora control state.

## 4. Call types

One state machine covers:

- 1:1 audio or video;
- group conversation calls;
- persistent drop-in rooms with explicit active-session instances;
- scheduled calls whose schedule and live instance are separate records;
- screen share as a track source, never a distinct ungoverned room.

Broadcast, recording, transcription, PSTN/SIP and livestream ingress/egress are
out of the initial gate. Each requires a separate consent, retention and abuse
review before activation.

## 5. State machine

Authoritative call state is revisioned and event-sourced enough to reconcile
retries and webhook disorder:

```text
created -> inviting -> ringing -> connecting -> active
    |          |          |           |          |
    +----------+----------+-----------+----------+-> ending -> ended
                                      |
                                      +-> reconnecting -> active | ending
```

Terminal reasons are explicit: declined, cancelled, no-answer, busy,
membership-revoked, kicked, network-timeout, server-failure, completed. A
device-local UI timeout never invents the server reason.

Rules:

1. Create is idempotent by authenticated caller plus `clientNonce`.
2. Every mutation carries `expectedRevision`; stale writes return conflict and
   the current snapshot.
3. Join requires current conversation membership, accepted message-request
   boundary, non-blocked relationship and an allowed device session.
4. Membership removal or session revoke increments `epoch`, invalidates future
   grants and removes the media participant immediately.
5. Webhooks are authenticated, deduplicated and can only confirm media-plane
   facts; they cannot grant Luxora authorization.
6. `ended` is immutable. A new session receives a new `callId` and room.

## 6. Grant model

The Luxora API is the only token issuer. After checking call membership, device
session, epoch, block policy and abuse limits, it issues a short-lived,
room-scoped LiveKit JWT:

- expiry no longer than two minutes for initial join;
- `roomJoin` only for the random room;
- no room create/list/admin/record/ingress/egress grants;
- publish sources restricted to microphone/camera/screen according to the
  current action and platform consent;
- subscribe permission limited to the same room;
- call-scoped opaque identity and bounded metadata;
- token refresh rechecks membership and epoch; an old token never extends the
  original grant expiry.

TURN uses coturn REST-style credentials derived from a server-only shared
secret, call/user-scoped username and expiry. Target TTL is five minutes. The
shared secret never reaches a client, logs, metrics or repository. Rotation
supports overlapping secrets for bounded drain, then rejects old credentials.

## 7. Target control API

These names reserve semantics; no endpoint is currently implemented:

- `POST /v1/calls` — idempotently create an authorized call.
- `GET /v1/calls/{callId}` — current revisioned snapshot.
- `POST /v1/calls/{callId}/invite` — add eligible members/devices.
- `POST /v1/calls/{callId}/accept|decline|cancel|leave|end` — revisioned actions.
- `POST /v1/calls/{callId}/join-grant` — short-lived SFU/TURN material.
- `POST /v1/calls/{callId}/tracks` — announce source intent/consent state.
- `POST /v1/internal/calls/livekit-webhook` — signed, replay-protected ingest.

Responses expose server time, `revision`, `epoch`, capability requirements and
an idempotent event cursor. Access to a conversation does not automatically
grant access to a historical call roster after retention expires.

## 8. Ringing and push

Ringing is a control-plane event, not proof that the target device displayed a
notification. Each invited device has explicit queued, pushed, delivered,
presented, accepted/declined or expired state. Push payload contains an opaque
call wake token and minimal type/version only; names, room, media keys and TURN
credentials are fetched after authentication.

Rate limits cover per-account, per-device, per-destination and risk/IP buckets.
Block/message-request policy is checked before push, presence disclosure or
ringing. Repeated declines, rapid fan-out and TURN allocation cost feed bounded
abuse controls without exposing content.

## 9. Tracks and screen sharing

Track sources are microphone, camera, screen-video and optional screen-audio.
Clients publish only after OS permission and an explicit action. The server
enforces allowed sources in the grant and reconciles published tracks against
that grant.

Screen share requires a persistent local indicator and deterministic
pause/resume/stop. Lock, app termination, permission loss, membership removal
or call end stops publication. A stale screen track is removed server-side on
disconnect timeout. Remote control is a separate, default-off future security
program and is not implied by screen sharing.

## 10. Availability and capacity

The production target separates Luxora call control from the media plane:

```text
Luxora clients -> authenticated Call Control -> metadata DB / durable events
       |                  |
       |                  +-> short-lived room/TURN grants
       v
regional TLS ingress -> LiveKit SFU nodes -> coturn pools
                           |
                           +-> Redis/control fabric only after HA evidence
```

SFU nodes and TURN pools are regional and capacity-aware. New joins drain away
from overloaded nodes; existing rooms remain pinned unless a tested migration
path applies. Relay capacity, egress bandwidth, packet loss, CPU, active tracks,
join latency and reconnect outcomes have explicit budgets and alerts. No public
availability or participant-count claim comes from vendor theoretical maxima.

## 11. Observability and retention

Allowed metrics use bounded dimensions: region, call type, media source,
network class, codec, outcome category and software build. Room/call/account IDs
are absent from metrics. Debug correlation uses short-lived random trace IDs in
restricted logs.

Call lifecycle records have a documented purpose and short retention. TURN IP
security logs have separate restricted retention. Quality samples are coarse
and unlinkable after aggregation. Recording/transcription is off and has no
storage path in this contract.

## 12. Required tests and gates

Calls remain unavailable until all of the following have evidence:

- state-machine property tests for duplicate, reorder, race and stale revision;
- authorization matrix for caller/invitee/non-member/removed/blocked/revoked
  device across every action and webhook;
- token tests for room/source/expiry/epoch scope and clock skew;
- signed webhook replay, forgery, reorder and delayed-delivery tests;
- TURN credential expiry, amplification/rate, peer allowlist and cost controls;
- Wi-Fi/cellular handoff, UDP blocked, TCP/TURN fallback, loss/jitter/bandwidth
  and reconnect lab on real devices;
- multi-node load, drain, crash, regional impairment and relay-exhaustion tests;
- microphone/camera/screen permission, indicator, background, lock and crash
  cleanup tests;
- VoiceOver, captions alternatives, Reduce Motion and one-handed controls;
- log/metric canaries proving no token, SDP, credential, content or stable user
  identifier leakage;
- independent security review; separate audited media-E2EE gate before any
  end-to-end protection claim.

## 13. Local scaffold limits

`docker-compose.calls.yml` binds every published endpoint to loopback, pins
multi-architecture image digests, drops Linux capabilities and uses a small
relay range. It deliberately disables TURN TLS for same-Mac testing and admits
only the fixed SFU peer inside its private Docker subnet. This topology must not
be copied to production.

Configuration validation or healthy metrics proves process wiring only. A real
Luxora call begins only after the call-control API, authorization, grants,
webhooks, clients and all relevant gates above are implemented.
